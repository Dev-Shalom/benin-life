# Friends, private messages and shared house visits

Real-player social features for Benin Life. Public place chat remains available through the existing Chat tab. These features have no admin dashboard controls or game-config switches.

## Current live-flow status (2026-10-09)

The invitation, server admission, shared-home rendering, movement broadcast and house-chat code shipped in commits `edac975` and `039311f`, and their database migrations were applied. Those code/deployment records do **not** establish that the full two-account player experience works. The user reports that an admitted visitor is not visibly inside the host's home, neither player sees the other's movement, and house chat is not working. Phase 0 is open until these reports are reproduced and fixed with two separate player accounts. See Phase 0 in `LAGOS_LIFE_REFERENCE_PLAN.md` for the required flow and acceptance criteria.

The current Phase 0 patch recognizes admitted visitors as being in the shared home, gives each player a stable separate arrival point, sends the current position when the private Realtime channel becomes ready, and adds an authenticated Leave house action. `npm run build`, rollback-only social/chat SQL suites, and `git diff --check` pass. `npm run lint` exits 0 with warnings. Live two-account verification is blocked by the browser's saved permission setting. Keep this patch on `codex/visual-quality`; do not push it to `main` or claim deployment until the flow is verified.

## Player flows

- Search players by username, send a friend request, and accept, decline or cancel requests. Only accepted friends can start direct conversations or send house invitations.
- Friends can exchange private text messages and recorded voice notes in Phone → Messages. The app applies no character-count limit to text; service, browser, and database resource limits still apply. Voice duration is not capped by the app, though browser recording and Supabase storage limits still apply.
- A host can select several friends and send them house invitations together. Each player can have one active invitation per host; invitations expire after 24 hours.
- Accepting an invitation means the guest is knocking. The host gets an event naming the guest, and the guest stays outside until the host opens Phone → Messages and admits them.
- Admission is server-checked: the host must be at their own home and not travelling. Up to eight guests may be admitted at once. The guest is moved into that host's private home and sees the host's home type, owner furniture, and saved furniture placements. Leaving the visit restores the guest's own home and layout.
- An admitted guest has a **Leave house** action in the home HUD. It calls the authenticated `social_leave_house()` RPC, which returns them directly to their own private home and restores their own housing layout; it does not rely on visiting the map or starting a travel action.
- Both host and guests see one another's live positions in the room; remote players walk the shared nav grid along the paths they broadcast (V2 below). The host can select an owned movable furniture item and place or rotate it. Its saved placement is shared with visitors currently in the home. Guests can walk around and use home activities, but cannot edit the host's furniture.
- A House chat shortcut opens a room shared by the people at that private home. It supports text and recorded voice notes. Selecting another player in the house offers the available food and drink items from the player's bag; accepted offers transfer one item to the recipient.
- Private homes have separate location records. They are omitted from the public map and normal travel destinations; only their owner and a guest admitted by that owner can see the location record. An invitation alone does not grant entry.
- **M3 (2026-10-10):** DMs share the place-chat bubbles (`src/panels/chatKit.tsx`): swipe right or use Reply to quote a message (`reply_to`), long-press or ⋯ for Delete for me / Delete for everyone (yours, within `chat.delete_everyone_hours`, default 48), scroll up for older messages (paged, at most 14 days back). Tombstones and read receipts arrive live through a Realtime UPDATE subscription on `player_messages`. Unfriend and Block moved into the conversation's ⋯ menu. `social_send_message` gained `p_reply_to`; the old 4-argument signature remains as a wrapper. RPCs and tests: docs/CHAT.md "M3", `supabase/tests/chat_upgrade_test.sql`.
- **M4 (2026-10-10):** Messages redesign (docs/CHAT.md "M4"): list with Chats / Groups, team news card, Message someone, filters, Message requests (friend requests plus door knocks / house invites live here now), conversation rows; each conversation has a **streak** (`social_streak`, consecutive WAT days where both of you messaged each other or one visited the other's home), Invite / Visit / Send money chips, blue bubbles with ✓ / ✓✓ receipts, quick replies and an emoji picker. The old multi-select "invite several friends" list was replaced by the per-conversation Invite chip. Migration `20261010000500_messages_v2.sql`, tests `supabase/tests/messages_v2_test.sql`.
- Players can block or unfriend a contact from the conversation (⋯ menu). Existing public chat's block controls also prevent private messaging and visits.

## V2: house visits that feel real (2026-10-11)

- **Same walls for everyone.** Guests render and walk on the host's layout: home type (`housing_id` is swapped on admission), the host's furniture and the host's saved placements (live via `player_house_furniture`), so `home3d/nav.ts` builds the same nav grid on every screen. The old remote avatar was drawn offset by the lot centre twice, which put visitors inside walls; fixed.
- **Real walking, no popping.** When a walk starts the owner sends one `path` broadcast in `house:<location>` (`{p: [x,z,...], f: faceTo, at}`, rounded to cm); the throttled `move` snapshots (100 ms moving / 280 ms idle) are unchanged. Each receiver walks the remote with the shared `sim/locomotion.ts` walker and the same gait as the local Sim, along those waypoints on its own grid. A snapshot alone (late join, reconnect, a missed path, a stop somewhere else) is reached by A* on the local grid; a gap over 4 m or no path = one quick fade-teleport. Activities come through the snapshot's `activity` (`activity#slot@pose`): the remote walks to the piece's spot, then sits / lies / cooks / scrubs / dances / hugs with the same blends. Idle avatars nudge apart (visual only, never into a blocked cell).
- **Two snapshot bugs fixed.** HomeScene compared seconds to milliseconds, so the owner sent a position only every 90 s (visitors popped from place to place); it now sends at the intended 100 / 280 ms, the house room sends the latest snapshot when a throttle window ends (the final stop is never dropped), and everyone re-sends their position when a newcomer joins.
- **Tap a person.** Tapping another player in the house (host or guest) opens a bottom sheet with their portrait and name: Cook a meal for them (needs a cooker), Watch a movie together (needs a TV; both sit on the sofa, side by side), Gist and chat, Dance together, Play Ludo or cards (needs a seat), Greet with a hug, plus Offer a drink or snack (`social_home_offer`, from the Bag) and Give a gift (`bank_transfer`, amount sheet; transfer rules apply). Interactions the house can't host show "Needs a TV" etc.
- **Server-authoritative.** `social_interact_request(p_user, p_kind)` checks both players are inside the same private home (owner at home + admitted guest, `bl_house_together`), not blocked, the host's furniture offers one of `requires`, no pending request between the pair, and the cooldown (`social.interact_cooldown_s`, default 60 s, per pair + kind). It writes `house_interactions` (pending, expires in 60 s) and an event `house_interact` to the other player, which arrives live (postgres_changes on `events`) as an Accept / Not now prompt with a draining countdown. `social_interact_respond(p_id, p_accept)` (the target only): decline / expired / accept; accept re-checks the house and furniture, both players must be free, charges the asker's `cost`, applies `effects` to both, sets both busy for `seconds` with the interaction's label (like `do_activity`, incl. the needs snapshot for the HUD), and tells the asker (`house_interact_reply`). Clients can only read their own rows; `interaction_types` is read-only for players and editable in Admin → Content → House interactions.
- **Poses per kind** (client, `src/api/interactions.ts` `IX_ROLE`; slot 0 = asker, 1 = the one who accepted): cook_meal = cook at the stove / sit; movie = both on the sofa (`relax_sofa`); gist, play_game = both seated (`sit_rest`, the second player takes another seat when the first is narrow); dance, greet = standing poses facing each other. A new admin kind just stands together.
- Files: `supabase/migrations/20261011000100_house_interactions.sql`, `supabase/tests/house_interactions_test.sql`, `src/api/interactions.ts`, `src/screens/game/HouseInteract.tsx`, `src/state/houseRoom.ts` (path broadcast), `src/art/home3d/engine/HomeScene.tsx` (`RemoteHomeAvatar`), `src/art/home3d/engine/poses.ts` (`poseDance`, `poseGreet`, covered by `scripts/pose-check.mjs`).

All writes use authenticated server functions. Friendship, message, home-invite, furniture-placement, and voice storage tables are protected by RLS. Direct messages are published to Supabase Realtime with participant and accepted-friend checks. Private home presence and broadcasts are authorized only for the owner and admitted guests at that home. Voice audio uses a private bucket and signed playback URLs; the custom player exposes playback-speed controls and no download control. This hides the download affordance, but media played in a browser cannot be made technically impossible to save using browser developer tools.
